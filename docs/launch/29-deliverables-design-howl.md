## 0 · 給 Edward 先讀（一頁懂）

你戳中的是 BeyondPath 整個產品最致命、也最容易被忽略的一塊——**「我到底買到了什麼？」**

### 你的直覺完全對，現況有三個破洞

| 破洞 | 現況 | 客戶體感 |
|---|---|---|
| **① 交付物在講工程黑話** | Confirm 步驟列「HubSpot API 整合 / React Dashboard 前端 / KPI 視覺化」 | 「這是什麼？我又不是工程師。我花 30 萬買到的是一堆我看不懂的英文名詞？」 |
| **② 交付物 = 勾選標籤、沒有結果** | 交付物只是個 checkbox + 報價加總、**沒對應「交什麼、怎麼算完成」** | 「勾完這些然後呢？最後我手上會拿到什麼東西？一個連結？一個檔案？一個能用的系統？」 |
| **③ 交付物跟里程碑脫鉤** | 交付物是一套（Confirm 勾的）、里程碑是另一套固定 30%/30%/40%、**兩者沒接** | 「我付第一筆 30% 是付了哪一項？我怎麼知道這 30% 該驗收什麼？」 |

### 一句話總結問題

**現在的「交付物」是「接案者要做的工」（工程任務），不是「客戶會拿到的成果」（交付成果）。這兩個是相反的視角。**

平台的存在價值就是**把客戶的不安變成確定**——「我付了錢、會在 X 時間、拿到 Y 東西、用 Z 標準驗收」。現在這條最重要的承諾鏈是斷的。

### 好消息：地基已經蓋好了

卡西法 5/28 做的 `milestone-detail.html` 已經有**檔案上傳 + 雲端儲存 + 版本歷史 + SHA-256 指紋 + 驗收釋款**——這是「最終交付狀態 + 雲端連結」的硬底子，**已經在了**。缺的不是基建，是**把「交付物」這個概念從工程語言翻成成果語言、再串到里程碑跟檔案上**。這是設計問題，不是工程問題。

### 我的建議（先給結論）

**PMF 第 1-10 案走「輕量版」**——交付物講人話（必做）+ 接案者自填交付說明（半自動）。**不要在還沒驗證需求前就蓋全自動結構化系統**。完整版留 v2，等案量起來、模式穩了再做。

工時：輕量版 **城堡 ~6-9 h**（人話對照表 + Confirm 文案改 + 串里程碑的輕量設計）。完整版 ~25-35 h（不建議現在做）。

## 1 · 交付物「講人話」（破洞 ① 的解法）

### 1.1 設計原則：講「客戶得到什麼結果」、不是「用什麼技術做」

這是文案層的一個視角翻轉，但它是整個產品信任感的關鍵：

| 維度 | 工程語言（現況 ❌） | 成果語言（要改成 ✅） |
|---|---|---|
| **主詞** | 接案者做的「工」 | 客戶拿到的「結果」 |
| **時態** | 動作（整合、開發、建置） | 完成態（你會有、你能、自動幫你） |
| **可驗證性** | 抽象（「整合」算完成了沒？） | 具體（「能登入看到自己數據」一試就知道） |
| **情緒** | 距離感、看不懂、不安 | 「喔我懂了、這就是我要的」 |

### 1.2 人話對照範例（5 vertical 抽樣）

> 來源：`components/data.standalone.jsx` 各 vertical 的 `parse.tasks[].zh`。現在這些直接被 `deliverablesFor()` 當交付物丟出來——這就是黑話的源頭。

#### 軟體開發（B2B SaaS 內部工具）

| 工程語言（現況） | 成果語言（人話版） |
|---|---|
| HubSpot API 整合 | 你的客戶與成交資料，自動同步進系統（不用再手動貼 Excel） |
| React Dashboard 前端 | 一個你自己就能打開看的銷售儀表板 |
| KPI 視覺化 | 業績漏斗、成交率、回本天數，一眼看懂的圖表 |
| Slack 整合 | 大金額訂單一有動靜，自動發訊息通知你的團隊 |

#### 設計品牌（D2C 品牌系統）

| 工程語言（現況） | 成果語言（人話版） |
|---|---|
| Brand DNA 工作坊 | 把你「想成為什麼樣的品牌」講清楚的一場深談 + 一份品牌定位文件 |
| Logo + 識別系統 | 你的 Logo、配色、字體，加一份「怎麼用才不會走樣」的使用手冊 |
| 包裝設計 × 4 | 4 款產品的完整包裝設計稿（可直接送印） |
| 品牌 GPTs 訓練 | 一個會用你品牌口吻寫東西的專屬 AI 助手 |

#### 短影音（個人品牌 KOL 內容工廠）

| 工程語言（現況） | 成果語言（人話版） |
|---|---|
| 週腳本 × 5 | 每週 5 支影片的腳本，照著拍就行 |
| 剪輯 × 5 | 每週 5 支剪好可直接上架的成片 |
| AI 配音 + 雙語字幕 | 中英雙語配音與字幕，做完直接給海外觀眾看 |
| 三平台排程 | 幫你排好 IG / TikTok / YouTube 的發布時間，不用自己一個個傳 |

#### AI Agent（電商客服自動化）

| 工程語言（現況） | 成果語言（人話版） |
|---|---|
| RAG 建置 + FAQ 灌入 | 一個讀過你所有 FAQ、答得出客戶問題的 AI 客服 |
| Multi-agent 路由 | 接單、退換貨、推薦商品分開處理，問什麼接對人 |
| LINE OA + Web Chat 接入 | 你的 LINE 官方帳號跟官網都能用這個 AI 客服 |
| 人工接手介面 | AI 答不了的時候，你的真人客服可以一鍵接手 |

#### 行銷增長（pre-PMF B2B SaaS 全套操盤）

| 工程語言（現況） | 成果語言（人話版） |
|---|---|
| 廣告投放（LinkedIn/Google/Meta） | 三大平台的廣告操盤，每月幫你帶進新名單 |
| 訪談 × 30 | 訪談 30 位你的真實客戶，整理成一份「他們為什麼買 / 為什麼不買」報告 |
| KPI 視覺化 | 每月一份看得懂的成效報告，知道錢花在哪、帶來什麼 |

### 1.3 翻譯的兩個鐵律

1. **不丟掉專業詞、但要加白話**——理想格式是「**成果語言（大字）+ 技術註腳（小字灰色）**」。例：
   ```
   即時數據儀表板               ← 客戶看的，大字、亮色
   你自己就能打開看的銷售儀表板    ← 一句話解釋，中字
   React + TypeScript Dashboard ← 技術註腳，小字、灰色（給內行客戶 / 接案者看）
   ```
   這樣不懂的人看得懂、懂的人也信得過。**不是把技術詞刪掉，是把它降級成註腳。**

2. **「結果」要可驗收**——人話版的每一句，理想上要能直接變成驗收標準（見第 2 節）。「能登入看到自己的數據」= 既是人話、也是驗收條件。一石二鳥。

## 2 · 每項交付物對應「成果 + 驗收標準 + 里程碑」（破洞 ② 的解法）

### 2.1 設計：每個交付物 = 4 件套

現在交付物只有「名字」。要補成 4 件：

| 欄位 | 是什麼 | 為什麼客戶需要 |
|---|---|---|
| **① 成果語言名稱** | 人話版的交付物名（第 1 節） | 看得懂買的是什麼 |
| **② 具體交付成果** | 交什麼——檔案 / 連結 / 帳號 / 報告 | 知道最後手上會拿到什麼實體東西 |
| **③ 驗收標準** | 怎麼算完成（客戶能自己判斷的條件） | 知道什麼時候該按「驗收通過」、釋款給接案者 |
| **④ 對應里程碑** | 這項屬於哪個付款階段（M1/M2/M3） | 知道每一筆錢付的是哪一項 |

### 2.2 完整範本（2 vertical 完整示範）

#### 範本 A · 軟體開發（B2B SaaS 內部工具 · 預算 28-38 萬 · 6 週）

| 成果語言名稱 | ② 具體交付成果 | ③ 驗收標準 | ④ 里程碑 |
|---|---|---|---|
| 客戶資料自動同步 | 一份「已串接完成」確認 + 同步設定截圖 | 打開系統，看到 HubSpot 的客戶資料確實出現了 | **M1（30%）** |
| 即時數據儀表板 | 可登入的 dashboard 連結 + 帳號密碼 + 一頁操作說明 | 你能用自己的帳號登入、看到自己公司的銷售數據 | **M2（30%）** |
| 一眼看懂的圖表 | 儀表板內含漏斗 / 成交率 / 回本天數 4 張圖 | 4 張圖都有數字、不是空的；數字跟你 HubSpot 對得上 | **M2（30%）** |
| 大訂單自動通知 | Slack 通知設定完成 + 一次測試通知截圖 | 你的 Slack 真的收到一則測試通知 | **M3（40%）** |

> M3 同時是「全案結案 + 完整交付」：所有原始碼 / 部署文件 / 後續維護說明一併交付，這時才放最後 40%。

#### 範本 B · 短影音（個人品牌 KOL · retainer 月費 36-54k · 第一個月穩定產線）

> 短影音是 retainer（月費）模式，里程碑邏輯不同——不是「一次交付分 3 段」，而是「每週一批、月底總驗收」。

| 成果語言名稱 | ② 具體交付成果 | ③ 驗收標準 | ④ 里程碑 |
|---|---|---|---|
| 每週 5 支腳本 | 每週一份含 5 支影片腳本的文件（雲端連結） | 每支腳本你看完覺得「照這個拍 OK」 | **每週交付（不單獨釋款）** |
| 每週 5 支成片 | 每週 5 支剪好的影片檔（雲端連結 / 下載） | 5 支都符合長度（60s 內）+ 你的品牌風格 | **每週交付** |
| 雙語配音字幕 | 影片內含中英配音 + 字幕（已嵌入成片） | 隨機抽 1 支，中英都對、字幕沒錯字 | **每週交付** |
| 三平台排程 | 一份「本月發布排程表」+ 已排程截圖 | IG/TikTok/YT 都看得到已排定的貼文 | **月底總驗收 → 釋放當月 retainer** |

> retainer 模式建議：**月底一次驗收當月所有產出 → 釋放當月月費**。週交付只是「進度可見」、不單獨釋款（不然金流碎到爆）。

### 2.3 驗收標準的設計鐵律

**驗收標準必須是「客戶自己一試就知道」的——不能是需要工程知識才能判斷的。**

| ❌ 不及格的驗收標準 | ✅ 及格的驗收標準 |
|---|---|
| 「API 整合測試通過」 | 「打開系統看到 HubSpot 的客戶資料」 |
| 「Dashboard 部署完成」 | 「我能用帳密登入看到我的數據」 |
| 「RAG 準確率 > 85%」 | 「我問 5 個常見問題，AI 答對至少 4 個」 |

驗收標準寫好了，「最終交付狀態」就自然成立——客戶不用猜「這算做完了嗎」，照著驗收標準一條條對就好。**這也是接案者的保護**：標準寫死，客戶不能事後無限加碼說「還沒好」。

## 3 · 交付物 → 里程碑 → 檔案 怎麼串（破洞 ③ 的解法）

### 3.1 現況：兩套各跑各的

```
Confirm 步驟              里程碑系統（milestone-detail.html）
─────────────            ──────────────────────────────
勾交付物（標籤）           固定 3 個里程碑 30% / 30% / 40%
報價加總                  每個里程碑能上傳檔案 + 驗收釋款
   │                          │
   └──────── 沒有連線 ─────────┘   ← 破洞在這
```

接案者上傳了一個檔案到「里程碑 1」——但這個檔案對應的是哪一項交付物？客戶不知道。客戶按「驗收通過 30%」——驗收的是哪些交付物？也不知道。

### 3.2 設計：把交付物「分配」到里程碑（輕量串接）

核心動作就一個——**Confirm 確認時，把選好的交付物分配到 3 個里程碑**。

```
Confirm 勾的交付物          自動 / 半自動分配           里程碑（已有檔案上傳）
─────────────             ─────────────            ──────────────────
客戶資料自動同步      ──┐
                       ├──→  M1（30%）  ──→  M1 頁面顯示「本階段交付：客戶資料同步」
即時數據儀表板      ──┐                          接案者上傳對應檔案
一眼看懂的圖表      ──┴──→  M2（30%）  ──→  M2 頁面顯示「本階段交付：儀表板 + 圖表」
大訂單自動通知 + 結案 ──→  M3（40%）  ──→  M3 頁面顯示「本階段交付：通知 + 完整交付」
```

### 3.3 分配怎麼做才不複雜（PMF 階段別過度工程）

**三選一，我建議走「半自動 B」：**

| 方案 | 怎麼分配 | 複雜度 | 適合階段 |
|---|---|---|---|
| **A · 全自動** | AI 拆解時依工時 / 依賴關係自動分配交付物到里程碑 | 高（要寫分配演算法） | v2+ |
| **B · 半自動（建議）** | AI 給一個「預設分配」（依任務順序均分到 3 個里程碑）、**Edward / 接案者可手動拖拉調整** | 中（一個拖拉 UI + 預設規則） | **PMF 現在** |
| **C · 純手填** | Confirm 後，里程碑頁面讓接案者自己打字寫「本階段交付什麼」 | 低（一個 textarea） | 最早期 / 第 1-3 案 |

**為什麼選 B 不選 A**：PMF 階段案量少（1-10 案）、每個案子模式差很大（一次性 vs retainer、4 項 vs 8 項），寫死的自動分配演算法很可能分錯、反而要人去改。**半自動 = AI 給草稿、人微調**，是這個階段投報率最高的。

**為什麼不只用 C**：純手填會讓「交付物清單」跟「里程碑說明」變兩份各打各的、容易不一致。B 至少保證里程碑的交付說明是從 Confirm 那份交付物來的、同一個 source of truth。

### 3.4 雲端連結這塊：已經有了，只差「貼回去」

Edward 問「該怎麼交付是否有對接好的流程與雲端連結」——答案是**有，但沒接到交付物上**：

- ✅ `milestone-detail.html` 已有：檔案上傳到 Supabase Storage、版本歷史、SHA-256、外部連結（給太大的檔案貼 Google Drive / Figma / GitHub）
- ✅ 驗收動作已有：客戶按「驗收通過」→ 觸發對應 % 釋款
- ⚠️ 缺的只是：**里程碑頁面要顯示「本階段對應哪些交付物」**，讓上傳的檔案有歸屬、驗收有對象

這是**前端顯示層的小工**，不是重建。串好之後，整條承諾鏈就完整了：

```
客戶看到人話交付物 → 知道分在哪個里程碑 → 接案者上傳檔案到對應里程碑
→ 客戶對照驗收標準驗收 → 釋款 → 拿到雲端連結 / 帳號 → 確定買到了什麼
```

## 4 · PMF 階段建議做到哪（別過度設計）

### 4.1 兩版對比

| 維度 | 輕量版（建議 PMF 做） | 完整版（留 v2） |
|---|---|---|
| **① 交付物人話** | ✅ 必做（人話對照表，每 vertical 一份） | ✅ 同上 |
| **② 成果 + 驗收標準** | 半結構：每 vertical 一份「範本」、接案者可微調 | 全結構：每項交付物都有獨立結構化欄位 + 系統驗證 |
| **③ 串里程碑** | 半自動 B：AI 預設分配 + 人手調 | 全自動 A：演算法依工時 / 依賴自動分配 |
| **④ 驗收狀態追蹤** | 用既有 milestone-detail 的驗收按鈕 | 每項交付物獨立驗收勾選 + 進度條 |
| **工時** | **城堡 ~6-9 h** | 城堡 ~25-35 h |

### 4.2 我的建議：第 1-10 案走輕量版

**理由（這是策略判斷，不只是省工）：**

1. **PMF 還沒驗證「交付物模式」**——現在連「客戶會不會在意交付物講不講人話」都還沒實證。先做最小可用版、看真實客戶反應，再決定要不要蓋全結構化系統。**先別為一個還沒被需求驗證的東西寫演算法。**

2. **案子模式差太大，全自動會錯**——一次性 vs retainer、4 項 vs 8 項，現在硬寫自動分配規則，10 個案有 6 個要人去改，不如直接半自動。

3. **人話對照表是真正的高價值、且一定不浪費**——不管之後做不做完整版，「工程詞 → 成果語言」這份對照表都會用到（Confirm 頁、里程碑頁、合約、甚至 landing page 都能用）。**這是穩賺的投資、優先做。**
