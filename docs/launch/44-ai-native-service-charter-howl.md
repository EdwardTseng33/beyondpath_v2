## TL;DR · 一頁 Edward 5 分鐘版

> **BeyondPath 不是「一個有 AI 功能的接案網站」，是「一條由 AI 貫穿的服務流」。** 差別不在「我們也接了 ChatGPT」——差別在：傳統接案平台把 AI 當成「網站上多一個按鈕」，我們把 AI 當成**整條服務的中樞神經**。傳統平台讓人去適應系統（填表、自己挑人、自己擔風險）；我們讓系統來服務人（AI 拆需求、AI 認證、AI 配對、AI 陪跑、AI 守約）。

| 項目 | 內容 |
|---|---|
| **新物種定義** | BeyondPath = **「AI 撮合的交付信任層」**——不是 job board（找人）、不是 freelance marketplace（比價）、是「替你判斷誰真的能交付、並陪你把案子跑完」的信任基礎設施 |
| **本質差異一句話** | 傳統平台賣「**選擇權**」（給你一堆人自己挑），BeyondPath 賣「**確定性**」（AI 已經幫你篩過、配過、會陪你跑完） |
| **產品結構原則** | 不是「網站 + 表單 + 人工」，是「**AI agent 貫穿的服務流**」——每個環節都問「這步 AI 能不能先做掉 80%，人只做最後 20% 的判斷」 |
| **服務體驗原則** | 雙邊在 AI 時代期待 5 件事：即時、智能拆解、低摩擦、可驗證的信任、AI 陪跑。每個體驗設計對照這 5 條 |
| **設計檢查指標** | 7 條可操作判準（§4）——城堡每個角色設計新功能時逐條對照，全綠才算「符合 AI 時代服務」 |
| **數位簽約 AI 形態** | 從「產 PDF + 線上簽」升級成「**AI 共筆合約 · 一條龍守約**」——AI 草擬條款 / AI 風險提示 / AI 里程碑拆解 / 合約串起配對-交付-金流 |
| **未來方向 Top 3** | ① AI 合約共筆 + 風險提示（PMF 可落地）② 交付陪跑 agent（每案一個 AI co-pilot）③ 一人公司營運 OS（長期北極星） |

**霍爾 verdict**：這份憲章的靈魂只有一句話——**「AI 時代的服務，不是讓人去用 AI，是讓 AI 來服務人。」** 傳統平台的隱含假設是「用戶會自己搞定」（自己寫需求、自己挑人、自己擔風險、自己追進度）。AI 時代把這個假設整個翻過來：**用戶只需要表達意圖，剩下的服務流由 AI 主動跑、人只在「非人不可」的節點介入。** 這不是炫技，這是把「一人撐不住的服務」變成「一人撐得住」的唯一方法——也是 BeyondPath 相對於 104 / Pro360 / Upwork 真正的、結構性的、抄不走的差異。

## 0. 為什麼要立這份憲章（策略洞察）

### 0.1 問題：AI 正在被「當成功能」而不是「當成骨架」

> 我假設 Edward 6/1 拍板的意圖是：**怕城堡未來做新功能時，不小心做成「傳統網站 + 一個 AI 按鈕」**——表面上有 AI，骨子裡還是傳統接案流。若這個假設不成立（例如 Edward 是要我做對外行銷敘事），請告知，我會換軸。

2026 年市場上 90% 的「AI 接案平台」都犯同一個錯：**把 AI 當成 feature checkbox**。他們的產品結構還是「傳統 job board + 表單 + 人工審核」，只是某個角落塞了一個「AI 推薦」按鈕。用戶體驗上，人還是得：自己寫清楚需求、自己從一堆候選人裡挑、自己判斷誰靠譜、自己追進度、自己擔交付風險。AI 只是「裝飾」，沒有改變服務的本質形狀。

**這正是危險所在。** 如果城堡未來每加一個功能都是「先想網站怎麼做，再想哪裡塞 AI」，那 BeyondPath 三五年後會變成「一個長得比較潮的 Pro360」——而不是新物種。

### 0.2 BeyondPath 已經有 AI native 的骨架，但需要被「立成憲章」才不會漂移

好消息是：BeyondPath 的骨架本來就是 AI native 的。看現有已落地的環節——

| 環節 | 現況 | AI native 在哪 |
|---|---|---|
| 需求進來 | `client-brief-parse` 真跑 Claude | **AI 拆解需求**，不是讓用戶填 20 個欄位 |
| worker 進來 | `worker-ai-interview` 7 段 Claude 訪談 + 自吹偵測 | **AI 認證 worker**，不是看履歷猜 |
| 配對 | `match-workers` 演算法 | **AI 配對**（往 5 維走），不是讓 client 自己翻名單 |
| 營運 | `daily-ops-digest` 每日簡報 | **AI 營運助理**，不是讓 Edward 自己輪詢 |
| 簽約 | `generate-contract-pdf` + `submit-signature` | 數位簽約（但 AI 介入還淺，見任務 2）|

**這 5 件事串起來，就是一個新物種：** client 表達意圖 → AI 拆 → AI 配 → AI 認證過的人交付 → AI 守約 → AI 盯營運。**人（Edward / worker / client）只在「判斷」「創造」「信任」這三類非人不可的節點出手。**

但「有骨架」不等於「不會漂移」。沒有憲章，下一個功能很可能又被做成傳統形狀。**這份憲章就是把「AI 是骨架不是裝飾」這件事，立成所有設計的北極星。**

### 0.3 這份憲章不是要「無腦加 AI」

反過來說也要警惕：**AI 時代服務 ≠ 把所有東西自動化。** §4 的檢查指標裡有一條鐵律——「非人不可的節點，AI 只輔助不替代」（撮合決策 / 撥款判斷 / 爭議仲裁 / worker 最終覆核）。AI native 的真意是「**AI 做掉 80% 的準備工作，人專注在 20% 的判斷**」，不是「人退場」。這既是品味問題（用戶要的是信任，不是冷冰冰的全自動），也是法律問題（媒合平台非服務提供者，撮合決策不能全自動）。

## 一、本質差異：AI 時代的接案媒合 vs 傳統

### 1.1 傳統平台的三個結構性弱點

| 平台 | 模式 | 結構性弱點（AI 時代的破口）|
|---|---|---|
| **104 外包 / 人力銀行** | 刊登職缺 / 接案需求 → 人海撈 → 自己聯絡 | 把「找人」當終點，**找到之後的判斷、交付、信任全部丟回給用戶**。用戶得自己面試、自己賭品質 |
| **Pro360（PRO360）** | 填需求 → 系統發給一堆 SP → SP 競價搶單 → 用戶比價挑 | 把「選擇權」當賣點，實際是**把判斷壓力轉嫁給用戶**。用戶收到 5 通報價電話，還是不知道誰真的會做。比價 = 逐底競爭，劣幣驅逐良幣 |
| **Upwork / Fiverr** | freelancer 自建檔案 → client 搜尋 / 發案 → 自己挑 → 平台託管金流 | 規模大但**信任靠評價數字 + 自己賭**。AI 時代的破口：評價可刷、檔案可美化，平台不對「這個人真的會用 AI 交付」負責 |

**三家的共同 DNA**：平台的角色是「**提供一個市場，剩下你自己來**」。用戶要自己寫需求、自己篩、自己判斷、自己擔風險。**平台不對「交付確定性」負責。**

### 1.2 BeyondPath 的本質翻轉：賣「確定性」不賣「選擇權」

> **傳統平台給你選擇權（一堆人自己挑），BeyondPath 給你確定性（AI 已經篩過、配過、會陪你跑完）。**

這是整個本質差異的核心句。展開來看，BeyondPath 的 AI native 結構優勢串起來是一個閉環：

```
傳統路徑（用戶自己扛）          BeyondPath 路徑（AI 服務流扛）
──────────────────            ──────────────────────────
用戶自己寫清楚需求       →     AI 拆解需求（client-brief-parse）
                                「你用人話說，我幫你結構化」
用戶自己看履歷猜誰會做   →     AI 認證 worker（worker-ai-interview）
                                「< 10% 通過、7 段訪談、自吹偵測」
用戶自己從名單挑人       →     AI 5 維配對（match-workers）
                                「我已經幫你算好 Top 3 + 為什麼」
用戶自己追進度怕掉鏈     →     AI 陪跑 + AI 守約（合約 + milestone）
                                「里程碑到點提醒、卡住主動 flag」
用戶自己擔信任風險       →     AI 認證資產 + 可驗證簽約 + 仲裁
                                「Tier 認證 + SHA-256 簽約 + 60 天仲裁」
平台不盯營運（用戶自助）  →     AI 營運助理（daily-ops-digest）
                                「平台主動看顧、Edward 一人撐得住」
```

**這個閉環就是新物種。** 不是「job board + AI 按鈕」，是「**AI 撮合的交付信任層**」——平台對「交付確定性」負責，而負責的方式是讓 AI 貫穿整條服務流。

### 1.3 為什麼這個差異「2026 年才可能」、且抄不走

- **抄不走的理由 1（結構先發）**：傳統平台的產品結構是十年前為「人海市場」設計的，要改成 AI native 等於砍掉重練。它們的 AI 只能貼在外圍。BeyondPath 是 AI native 出生，骨架就是 AI。
- **抄不走的理由 2（信任飛輪）**：AI 認證 + 履約評鑑數據回推認證等級（Framework 的 B5→B3 飛輪），數據越跑越準。後進者沒有這個數據底。
- **抄不走的理由 3（華語區 AI 顧問定位）**：Mercor（年營收 4.5 億美元）證明 AI 工作者媒合是大市場，但它只服務 AI 實驗室。一般華語區中小企業沒人服務——這是藍海縫隙（Framework §2）。

## 二、產品結構原則：AI agent 貫穿的服務流

### 2.1 核心原則：從「頁面思維」到「服務流思維」

**傳統做法（頁面思維）**：先想「要做幾個頁面、每頁放什麼表單、後面接誰人工處理」。產品 = 頁面集合。

**AI 時代做法（服務流思維）**：先想「用戶的意圖如何沿著一條 AI 貫穿的流動完成，人只在非人不可的節點介入」。產品 = 一條服務流，頁面只是這條流的「出入口」。

### 2.2 服務流的結構單元：每個環節都是「AI 預備 → 人判斷」

AI native 的產品結構，每個環節都拆成兩層：

```
┌─────────────────────────────────────┐
│  環節 N                               │
│  ┌──────────────┐  ┌──────────────┐  │
│  │ AI 層（80%）  │→ │ 人層（20%）   │  │
│  │ 預備 / 草擬   │  │ 判斷 / 拍板   │  │
│  │ 結構化 / 打分 │  │ 創造 / 信任   │  │
│  └──────────────┘  └──────────────┘  │
└─────────────────────────────────────┘
```

舉例（已落地的）：
- **worker 認證**：AI 跑 7 段訪談 + 算 L_score + 自吹偵測（80% 準備）→ Edward 看 AI 初評後拍板 approve/hold/reject（20% 判斷）
- **配對**：AI 算 Top 3 + match score + 為什麼（80% 準備）→ Edward 確認派誰（20% 判斷）
- **營運**：AI 收斂成每日簡報 + 標優先級（80% 準備）→ Edward 處理該他處理的事（20% 判斷）

**這個「AI 預備 → 人判斷」是 BeyondPath 產品結構的最小單元。** 任何新功能都該能拆成這個結構。如果一個新功能「全是人工」或「全是自動沒人把關」，它就不符合 AI 時代服務原則。

### 2.3 三條產品結構鐵律

| # | 鐵律 | 反例（不該做的）|
|---|---|---|
| **S-1** | **意圖優先，表單其次** — 讓用戶用人話表達意圖，AI 負責結構化。不要讓用戶填一堆欄位去適應系統 | ❌ 開一個 20 欄位的發案表單讓 client 自己填齊 |
| **S-2** | **AI 預備、人判斷** — 每個決策環節，AI 先做掉準備工作 + 給建議，人只做最後判斷 | ❌ 讓 Edward 從零開始看原始申請資料、無 AI 初評 |
| **S-3** | **流動連續，不要斷點** — 服務流環節之間資料自動流動（brief → 配對 → 合約 → milestone → 金流），不要每環節重新填一次 | ❌ 簽約時要 client 重新填一次案件資訊（brief 已經有了）|

### 2.4 對齊現況：12-step flow 已經是服務流，但要守住

Framework 的 12-step flow（Pre-intake → AI 拆解 → 配對 → 簽約 → milestone → 評鑑）本身就是服務流結構。**憲章要守住的是：未來每加一步，都不能破壞這條流的連續性，不能讓某一步退回「純表單 + 人工」。**

## 三、服務體驗原則：雙邊在 AI 時代期待什麼

AI 時代的用戶（無論發案者 / 接案者）被 ChatGPT / Linear / Stripe 這些產品「養刁」了，期待 5 件事。**每個體驗設計都要對照這 5 條。**

### 3.1 五大體驗期待

| # | 期待 | 發案者視角 | 接案者視角 | 設計含義 |
|---|---|---|---|---|
| **E-1 · 即時** | 不想等 | 發完 brief 想馬上知道「有沒有人能做」 | 申請完想馬上知道「我過了沒」 | 任何環節 > 24h 無回應 = 體驗破口。即時不到就要「即時告知進度」（如「24h 內配對」明示）|
| **E-2 · 智能拆解** | 不想自己想清楚 | 用人話說需求，AI 幫我結構化 + 補我沒想到的 | AI 訪談引導我講出我的能力，不用自己寫漂亮履歷 | AI 主動拆解、主動補問，不是被動收表單 |
| **E-3 · 低摩擦** | 不想跳很多步 | 不想填 20 欄、不想重複填、不想裝 app | 不想為了接案自己寫一堆檔案 | 每多一個欄位 / 一次跳轉 / 一個帳號步驟 = 流失。摩擦 = 流失 |
| **E-4 · 可驗證的信任** | 不想賭 | 想知道「這個人真的會用 AI 交付」有憑據 | 想要「我通過認證」是可展示的資產 | 信任要「可驗證」不是「靠感覺」——Tier 認證 / 簽約 hash / 仲裁機制都是信任憑據 |
| **E-5 · AI 陪跑** | 不想自己追 | 案子卡了 AI 主動提醒我，不用自己盯 | 交付到點 AI 提醒我，不用怕漏 | AI 不是交付完就消失，是「陪跑到結案」的 co-pilot |

### 3.2 體驗的品牌調性：AI 原生 + 專業溫暖

AI native 不等於冷冰冰。BeyondPath 的體驗調性是「**AI 原生 + 專業溫暖**」（對齊 uiux-design-excellence §一）：
- AI 說話像「靠譜的顧問」，不像「系統 log」。✅「我幫你把需求整理成這樣，你看對不對」 ❌「需求解析完成，共 5 筆任務」
- 信任感來自「透明」——AI 做了什麼、為什麼這樣建議，要讓用戶看得到（AI 透明度原則）。
- 溫暖來自「主動照顧」——AI 主動提醒、主動補問、主動報平安，讓用戶覺得「有人（AI）在幫我盯著」。

### 3.3 反模式警告（體驗破口）

- ❌ **AI 黑箱**：給結果不給理由（「配對 92 分」但不說為什麼）→ 違反 E-4，信任崩。**這正是 doc 08 修掉的 hardcoded 92 分問題的根本教訓。**
- ❌ **填表地獄**：用「全面」當藉口要用戶填一堆 → 違反 E-3。
- ❌ **交付即棄**：配對完 AI 就消失，後面全靠人追 → 違反 E-5。
- ❌ **過度自動化**：撮合 / 撥款 / 仲裁全自動沒人把關 → 違反信任，且踩法律界線。

## 四、設計檢查指標：城堡每個角色的「AI 時代服務」檢查清單 ⭐⭐

> **這是這份憲章最可操作的部分。** 城堡任何角色（霍爾 / 卡西法 / 女巫 / 蕪菁頭 / 馬魯克 / 蘇菲 / 沙利曼）設計或審查任何新功能 / 新服務時，逐條對照。**全綠才算「符合 AI 時代服務」；任一條紅，退回重想。**

### 4.1 七條檢查指標（AI Native Service Checklist · ANSC）

| # | 檢查問題 | 綠（通過）| 紅（退回）| 主要把關角色 |
|---|---|---|---|---|
| **ANSC-1 · 意圖優先** | 這個功能讓用戶「表達意圖」還是「填表去適應系統」？ | 用戶用人話表達，AI 結構化 | 開一堆欄位讓用戶自己填齊 | 蕪菁頭（用戶意圖）|
| **ANSC-2 · AI 預備 → 人判斷** | 這個環節 AI 有沒有先做掉 80% 準備工作，人只做最後判斷？ | AI 草擬 / 打分 / 預備，人拍板 | 全人工 / 或全自動沒人把關 | 霍爾 + 卡西法 |
| **ANSC-3 · 流動連續** | 資料有沒有從上一環節自動流到這一環節，還是要用戶重填？ | 上游資料自動帶入 | 每環節重新填一次 | 卡西法（技術串接）|
| **ANSC-4 · AI 透明** | AI 給的結果有沒有附「為什麼」？用戶看得到 AI 做了什麼嗎？ | 結果 + 理由 + 可追溯 | 黑箱給數字不給理由 | 女巫（設計）+ 霍爾 |
| **ANSC-5 · 即時或明示進度** | 用戶提交後馬上有回應，或至少明確告知何時有結果？ | 即時 / 或「X 小時內 email」明示 | 提交後石沉大海 | 蕪菁頭 + 卡西法 |
| **ANSC-6 · 摩擦最小** | 這一步能不能砍掉？欄位能不能少？跳轉能不能省？ | 已砍到不能再砍 | 為「完整」加步驟 | 女巫 + 蕪菁頭 |
| **ANSC-7 · 信任可驗證 + 守住人類節點** | 信任有沒有可驗證憑據？非人不可的節點有沒有守住（不全自動）？ | 有憑據 + 撮合/撥款/仲裁/覆核仍人工 | 靠感覺 / 或越界全自動 | 沙利曼（Gate 5）+ 霍爾 |

### 4.2 怎麼用這份清單（操作 SOP）

1. **設計新功能前**：提案者（通常霍爾出 spec）先自評 7 條，附在 spec 裡。
2. **Gate 審查時**：對應角色（見上表「主要把關角色」）逐條打勾。
3. **任一條紅**：退回重想，不是「之後優化」——AI 時代服務的形狀是設計出來的，不是補出來的。
4. **季度盤點**（對齊 Know-3）：現有功能也用這 7 條複查一次，抓「漂回傳統形狀」的功能。

### 4.3 一句話記憶版（給城堡每個角色背下來）

> **「用戶表達意圖（1），AI 預備人判斷（2），資料自動流動（3），AI 給結果附理由（4），提交即有回應（5），摩擦砍到最少（6），信任可驗證且人類守住關鍵節點（7）。」**

## 五、未來方向：AI 時代延伸的新功能 / 新服務

> 排優先序、標「PMF 務實（現在可落地）」vs「長期北極星（押後）」。**對齊 doc 04 的 hold scope——PMF 階段刻意克制，不超綱。**

### 5.1 優先序總表

| 優先 | 方向 | 屬性 | PMF 階段做不做 | 對應 Framework |
|---|---|---|---|---|
| **P0** | AI 合約共筆 + 風險提示（見任務 2 §六）| PMF 務實 | **第一步可落地** | B4 合約履約 |
| **P0** | AI 營運助理（daily-ops-digest 已落地，繼續深化）| PMF 務實 | 已落地、Phase 1-2 推進 | 營運層 |

| **P1** | AI 配對的「為什麼」可解釋層（補 E-4）| PMF 務實 | soft launch 後補 | B1 需求媒合 |
| **P2** | AI 履約評鑑 + 認證飛輪（B5→B3 數據閉環）| 中長期 | Y1 Q3+ | B5 + B3 |
| **P3** | 一人公司營運 OS（客戶 / 履約 / 認證 / 工具帳戶層）| 長期北極星 | Y4-5 純 narrative | L4 願景 |

### 5.2 P0/P1 三個方向展開（Top 3）

#### 方向 ① · AI 合約共筆 + 風險提示（P0 · PMF 務實）

詳見任務 2（§六）。一句話：把現有「產 PDF + 線上簽」升級成「AI 幫雙方共筆條款 + 主動提示風險 + 智能拆里程碑」。**第一步**：AI 根據 brief + tier + 預算，自動草擬合約條款初稿 + 標出「這份合約對你最該注意的 3 個風險點」。

#### 方向 ② · 交付陪跑 agent（每案一個 AI co-pilot）（P1）

**洞察**：現在配對完成後，AI 就「下班」了，後面 milestone 進度全靠 Edward 人工盯（doc 40 在解這個，但那是「給 Edward 的營運助理」，不是「給每個案子的陪跑」）。

**AI 時代該怎麼做**：每個進行中的案子，配一個輕量「交付陪跑 agent」——
- 對 client：milestone 到點主動提醒「該驗收了」、卡住主動 flag「這個案 worker 2 天沒動，要我幫你提醒嗎」
- 對 worker：交付到點提醒、acceptance criteria 沒達標時主動提示
- 對雙方：把「自己追進度」變成「AI 陪你跑完」（對應體驗 E-5）

**PMF 第一步**：不用做複雜的 agent，先在每日簡報 + milestone 狀態變化的 email 裡，加「AI 陪跑語氣」的主動提醒。10-30 案階段再做成獨立 co-pilot。

#### 方向 ③ · 一人公司營運 OS（P3 · 長期北極星 · 純 narrative）

**這是 Framework 的 Y4-5 願景，PMF 階段一行 code 都不寫。** 但它是憲章的「北極星終點」——當 BeyondPath 把「AI 撮合的交付信任層」做透，下一步自然延伸到「一人公司的營運基礎設施」：客戶關係 / 履約管理 / 認證資產 / AI 工具帳戶，全部由 AI 服務流貫穿。**這個願景定義了城堡所有設計的「最遠方向」——每個功能都該問：這一步有沒有讓我們更接近『一人公司的 AI 營運 OS』。**

### 5.3 明確不做（守 hold scope）

- ❌ AI 自動撮合（不經人判斷直接派案）—— 違反 ANSC-7 + 法律界線
- ❌ AI 自動撥款 / 自動劃帳 —— 同上
- ❌ AI 自動仲裁判決 —— 爭議必人工
- ❌ PMF 階段堆 ML / 預測模型 —— 數據量不夠，炫技不減負（對齊 doc 40 Phase 3 押後）

## 六、任務 2 · 數位簽約在 AI 時代的服務形態

### 6.1 現況盤點（已落地）

| 元件 | 現況 | AI 介入程度 |
|---|---|---|
| `generate-contract-pdf` | template fill（pdf-lib 填欄位：當事人 / 案件 / 服務費 / 付款 / NDA / 簽名框）| **無 AI**（純模板填空）|
| `submit-signature` | 線上簽 + JWT 驗證（contract_sign / role match）+ IP rate limit（5 fail/15min）+ SHA-256 hash（圖 + timestamp）+ 簽名圖上傳 Storage | 無 AI（純安全機制）|
| `resend-contract-certificate` | 雙簽完成後寄憑證 | 無 AI |
| `contract-verify.html` | 查驗頁（憑 hash 驗合約真偽）| 無 AI |
| 決策層 | Edward 拍板「自家簽 + 第三方時間戳」| — |

**現況判定**：數位簽約的「**安全 / 信任機制**」已經做得很扎實（JWT 三層 + SHA-256 + IP rate limit + 可驗證憑證）——這對應體驗 E-4「可驗證的信任」，是強項。**但 AI 介入幾乎是零**——合約是模板填空，沒有 AI 草擬、沒有風險提示、沒有智能拆解。這正是「有數位、但還不夠 AI native」的環節。

### 6.2 願景：從「數位簽約」到「AI 共筆合約 · 一條龍守約」

> **數位簽約的 AI native 終局：合約不是一份「填好讓你簽的文件」，是一個「AI 陪你談清楚、提醒你風險、串起整個交付與金流的活的協議」。**

對照 ANSC 七條檢查，現況合約系統的缺口：
- ANSC-1 意圖優先：❌ 合約是模板，沒有「用 brief 的意圖自動生成貼合的條款」
- ANSC-2 AI 預備：❌ 沒有 AI 草擬條款初稿
- ANSC-4 AI 透明：❌ 沒有「這份合約對你該注意的風險」提示
- ANSC-3 流動連續：⚠️ 部分（從 intake + worker 帶入基本資料），但 milestone / 金流還沒在合約層串起來
- ANSC-7 信任可驗證 + 人類守住：✅ 強（hash + 憑證 + 人類簽署）

### 6.3 AI 時代這條服務怎麼跑得更好（4 個 AI 介入點）

#### 介入點 A · AI 草擬合約條款（補 ANSC-1 + ANSC-2）

**現在**：generate-contract-pdf 把固定模板填空。
**AI 時代**：AI 讀 `client-brief-parse` 已經拆好的需求結構（vertical / tasks / budget / timeline）+ worker tier，**自動草擬一份「貼合這個案子」的合約條款初稿**——不是一份通用模板，是「這個案子該有的條款」（例：設計案自動帶入「原始檔交付 + 字體授權」條款，GTM 案自動帶入「數據 / 帳號權限」條款）。Edward / 雙方在初稿上改，不是從零填。

#### 介入點 B · AI 風險提示（補 ANSC-4）

**AI 時代**：合約生成後，AI 主動標出「這份合約對你（client / worker 各自視角）最該注意的 3 個風險點」——用人話講：
- 對 client：「這個案沒寫驗收標準，建議補上 milestone 1 的 acceptance criteria，否則容易爭議」
- 對 worker：「這個案 IP 條款是『完成即歸 client』，你中途的設計探索稿也算在內，確認你 OK」

這是 AI native 合約相對於「一份大家都不看就簽的 PDF」最大的價值——**AI 是雙方的「合約讀者」，把法律語言翻成風險人話。** 直接對應 BeyondPath「AI 撮合的交付信任層」定位：信任不只在認證，也在「簽約時你真的懂你簽了什麼」。

#### 介入點 C · AI 智能里程碑拆解（補 ANSC-2 + ANSC-3）

**現在**：付款分 30/30/40 三段是寫死的。
**AI 時代**：AI 根據 brief 的 tasks + timeline，**建議這個案該怎麼拆里程碑**——不是固定三段，是「這個案有 5 個任務，建議拆成 3 個 milestone：M1 含 task 1-2（兩週）、M2 含 task 3（一週）...，每個 milestone 對應一筆款」。拆完的 milestone 直接流進交付追蹤（ANSC-3 流動連續），不用簽完約再手動建 milestone。

#### 介入點 D · 合約串起配對 / 交付 / 金流一條龍（補 ANSC-3）

**這是最關鍵的「一條龍」洞察。** AI 時代的合約不是孤立的一份 PDF，是**整條服務流的中軸**：

```
配對成功（match-workers 輸出）
   ↓ 自動帶入當事人 + 案件 + tier
AI 草擬合約（介入點 A）+ AI 風險提示（B）+ AI 拆 milestone（C）
   ↓ 雙方線上簽（submit-signature · 現有安全機制）
   ↓ milestone 自動建立（介入點 C 拆好的）
交付追蹤（每個 milestone 對應驗收 + 一筆款）
   ↓ milestone 驗收觸發
金流（B 代收代付 · 綠界 · 對齊 5/29 拍板）
   ↓ 結案
雙邊 NPS + 履約數據回認證飛輪（B5→B3）
```

**合約是把「配對」「交付」「金流」「認證」縫成一條龍的那根線。** 現在這幾塊是分開的（合約一個 function、milestone 一個、金流一個），AI native 的願景是讓它們**從合約這個中軸自動流動**——簽完約，milestone 自動就緒、金流節點自動對齊、結案數據自動回飛輪。

### 6.4 PMF 第一步（務實落地 · 不超綱）

> **不要一次做完 A/B/C/D。** PMF 階段（< 30 案、1 人營運），第一步只做「最有感、風險最低、最對齊定位」的一塊。

**第一步推薦：介入點 B（AI 風險提示）+ 介入點 A 的輕量版。**

理由：
1. **最對齊定位**：「AI 幫你看懂合約風險」直接強化「AI 撮合的交付信任層」——信任是 BeyondPath 的核心賣點，風險提示是信任的具體體現。
2. **風險最低**：不碰簽約安全機制（已扎實）、不碰金流（敏感）、不改 milestone 結構。只在「合約生成後、簽署前」加一段 AI 風險摘要。
3. **技術最省**：`client-brief-parse` 已經接了 Claude API、合約資料已經有結構。一次 LLM call（讀合約 + brief → 輸出「雙方各自該注意的 3 個風險點」），成本可忽略（對齊 client-brief-parse 的 NT$ 0.5-0.8/case 量級）。
4. **最有感**：client / worker 收到合約 email 時，附一段「BeyondPath AI 幫你劃了重點」——這是傳統平台給不了的體驗，第一個真案就能感受到差異。

**第一步明確不做**（押後）：
- 介入點 C 的 milestone 自動拆解 → 10-30 案階段（要先看真案怎麼拆才有 ground truth）
- 介入點 D 的金流一條龍 → 金流（B 代收代付）正式站跑通 + 累積 5 案後再串
- AI 草擬「完整」條款 → 先用現有模板 + AI 補「案件專屬條款建議」，不取代律師 review 的條款框架（沙利曼 Gate 5 把關，法律框架仍人類定）

### 6.5 數位簽約 AI 形態的檢查（對照 ANSC）

| ANSC | 第一步後 | 完整願景後 |
|---|---|---|
| 1 意圖優先 | ⚠️ 部分（A 輕量版帶入 brief 意圖）| ✅（A 完整草擬）|
| 2 AI 預備 | ✅（B 風險提示 = AI 預備）| ✅（A+B+C 全預備）|
| 3 流動連續 | ⚠️（合約帶入 brief）| ✅（D 一條龍）|
| 4 AI 透明 | ✅（B 風險提示 = 透明）| ✅ |
| 5 即時 | ✅（合約生成即附風險）| ✅ |
| 6 摩擦最小 | ✅（不加步驟，只加價值）| ✅ |
| 7 信任可驗證 + 人類守住 | ✅（簽約安全機制 + 法律框架人類定）| ✅ |

*Edward，這份憲章的靈魂我幫你想清楚了：AI 時代的服務，不是讓人去用 AI，是讓 AI 來服務人。傳統平台把「你自己搞定」當預設，我們把它翻過來——用戶只表達意圖，AI 跑完整條服務流，人只在非人不可的節點出手。§4 的七條檢查指標就是用來守住這件事，讓城堡每加一個功能都不會漂回傳統形狀。數位簽約的 AI 形態，第一步只做「AI 幫你看懂合約風險」——最對齊我們的信任層定位、風險最低、第一個真案就有感。其餘的，等真案跑出 ground truth 再串成一條龍。*
