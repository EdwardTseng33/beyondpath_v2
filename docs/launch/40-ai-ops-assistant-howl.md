## TL;DR · 一頁 Edward 5 分鐘版

> **問題不是「沒通知」，是「通知是碎的」。** 現在 Edward 收 4 封即時 email + 要主動輪詢 5 個地方（admin 各 tab + Slack）才能拼出全局。AI 營運助理把這件事反過來：**AI 主動看顧整個平台，每天推一份「今天平台怎麼了 + 你該做哪 N 件事 + 哪裡要警戒」給你，剩下的它自己盯。**

| 項目 | 內容 |
|---|---|
| **AI 營運助理 4 層** | 觀察（AI 盯什麼）→ 輔助（AI 自動做/預備）→ 提醒（哪些非 Edward 不可、何時提醒）→ **每日簡報**（核心交付） |
| **核心交付** | 每天台灣時間 **09:00** 一封「BeyondPath 每日營運簡報」email（+ admin dashboard 同步顯示） |
| **第一步最小可行** | **現有 `notify-edward.ts` + 一個每日簡報 Edge Function（cron 09:00）**——不重造任何東西、一個新檔就有感 |
| **策略邏輯** | 1 人營運的 bottleneck 不是「做不完」，是「不知道該做什麼 + 怕漏接」。AI 助理把 Edward 從「輪詢者」變成「被服務的營運長」 |
| **不做的事** | 不替 Edward 拍板（覆核 worker / 確認配對 / 撥款判斷永遠人工）、不碰真金流自動劃帳、不在 PMF 階段堆 ML |

**霍爾 verdict**：這件事的靈魂不在「多發幾封通知」——多發通知只會讓 Edward 信箱更吵。靈魂在**「AI 幫你把雜訊收斂成一張每天看一次的清單」**。即時通知只留「真的等不了」的事，其餘全部塞進每日簡報。**少即是多——一封好簡報 > 二十封即時 email。**

## 0. 為什麼現在要做（策略洞察）

### 0.1 痛點不是技術洞，是「認知負荷洞」

馬魯克 doc 37 §六說得很準：Edward 現在要主動「輪詢」5 個地方才知道全局，<5 並行案撐得住、超過就漏接。但我要往上提一層看——

**真正的問題不是「系統不通知」，是「通知的形狀不對」。** 現在 `notify-edward.ts` 已經會發 4 封即時 email 了，可是：

1. **即時 email 是「事件視角」，Edward 需要的是「狀態視角」**——他不想要 20 封「發生了 X」，他想要 1 句「今天有 3 件事等你，最急的是 A」。
2. **即時 email 沒有優先級**——worker 申請和合約簽完用同樣的紅色感歎號，Edward 無從判斷先處理哪個。
3. **即時 email 不報「沒發生的事」**——「這個案卡 3 天沒動」「這週沒有新發案」這種「靜默異常」，事件式通知永遠不會告訴你，但它們往往才是 PMF 階段最致命的信號（案源荒 / worker 荒）。

AI 營運助理的策略價值就在這——**它報「狀態」「優先級」「沒發生的事」，這三件事即時通知做不到。**

### 0.2 競品對標：營運助理是 2025-2026 的明確趨勢

- **Linear（2025 下半年新 dashboard + AI triage）**：把「該你看的 issue」自動排序推給你，而不是讓你逐條翻。我們學它的「為你收斂、不為你決定」。
- **Stripe Dashboard / Radar**：金流對帳 + 異常標紅，AI 摘要當日帳務狀態。我們學它的「對帳摘要」而非逐筆 webhook。
- **Mercury / Ramp（財務營運助理）**：每日/每週把「現金流 + 待辦 + 異常」收斂成一封 digest。我們學它的「digest 形態」。
- **Attio（2025 AI CRM）**：自動歸類 + 主動提醒 follow-up 時點。我們學它的「該追的事到點提醒」。

**差異化 angle**：上面這些都是「單一職能助理」（金流的 / CRM 的 / 工程的）。BeyondPath 是**雙邊市集**，AI 助理要同時盯「供需兩邊 + 中間的撮合鏈 + 金流」——這個「跨整條撮合鏈的營運視角」是我們的獨特位置。我們不是做第 N 個 dashboard，是做**「一人營運雙邊市集的副駕駛」**。

### 0.3 對齊 PMF 階段（不超綱）

doc 04 階段定位：Y1 PMF、邀請制 soft launch、<5 並行案、北極星=雙邊 60 天回購。

**這意味 AI 營運助理在這階段的目標只有一個：讓 Edward 一人撐得住前 10-30 案，不漏接、不焦慮、不需要每天輪詢。** 不是做給 1000 個案用的自動化引擎。所以本藍圖刻意**克制**——P0 只做一封每日簡報，ML / 自動劃帳 / 預測全部押到後期。

## 1. 第一層 · 自動觀察（AI 盯什麼）

AI 助理每天掃一次平台狀態（cron），歸類成 6 個觀察維度。**這層只「看」，不「做」，不「擾」。**

| # | 觀察維度 | AI 盯的資料 | 信號定義（觸發關注） |
|---|---|---|---|
| O-1 | **待配對案** | `client_intakes` status=submitted 且無對應 contract | 任一 brief 送出 > 24h 仍未發邀請 = 黃；> 48h = 紅 |
| O-2 | **待審 worker** | `worker_applications` status=pending | 任一申請 > 24h 未審 = 黃；> 72h = 紅（對齊 ack email 對用戶承諾的 72h） |
| O-3 | **卡住 / 逾期案** | `contracts` + `milestones` 的 status × due_date | 簽約後 worker 未接 > 24h / milestone 標 delivered 後 client 未驗 > 5 天（逼近 7 天自動通過）/ 雙方簽署啟動後一方 > 3 天未簽 |
| O-4 | **金流對帳狀態** | `commission_records` / `commission_collected_total_ntd` / `client_paid` | 路徑 D 下：worker ack 收款 > 48h 延遲 / 抽佣逾期 > 14 work days 未收 / 應收 vs 已收不一致 |
| O-5 | **異常** | rate limit log / admin 登入 log / arbitration / 退件次數 | 發案防灌爆觸發 / admin 異常登入 / 進入仲裁 / 同案退件達 2 次（逼近第 3 次觸發仲裁） |
| O-6 | **雙邊供需失衡** ⭐ | `worker_applications`(approved) by vertical vs `client_intakes` by vertical | 某領域有發案但 0 個可配 worker（**worker 荒**）/ 連續 7 天 0 新發案（**案源荒**）/ 某 worker 連續被推 3 次都沒接（供給假性充足） |

**O-6 是策略上最重要、也最容易被忽略的一層**——前 5 個維度即時通知勉強能覆蓋，但「供需失衡」是**靜默信號**，沒有任何單一事件會觸發它，只有「站在整盤上每天看一次」才看得出來。這正是 AI 助理相對於即時 email 的核心價值，也直接餵養蕪菁頭 doc 36 的「雙邊健康指標」。

## 2. 第二層 · 自動輔助（AI 自動做 or 預備好讓 Edward 一鍵）

**原則：AI 做「準備工作」和「草稿」，把 Edward 的決策成本降到最低；但「按下確認鍵」永遠是 Edward。** 這是信任邊界，也是法律邊界（媒合平台非服務提供者，撮合決策不能全自動）。

| # | 輔助動作 | AI 做什麼 | 落點 | 現況基礎 |
|---|---|---|---|---|
| A-1 | **配對推薦預備** | 新 brief 進來，AI 預跑 5 維配對演算法，把 Top 3 候選 + match score + 「為什麼推薦」一句話**預先算好**放進簡報，Edward 點開 admin 已經看到結果 | 每日簡報「待你確認配對」段 | 5 維配對演算法已有（doc 08） |
| A-2 | **worker 預審打分** | 新申請進來，AI 七段訪談認證 + 自吹偵測 + L_score + skill matrix **已自動跑完**，簡報直接呈現「AI 初評：建議 approve / hold / reject + 理由」 | 每日簡報「待你覆核」段 | AI 七段訪談 + 自吹偵測已有 |
| A-3 | **通知/回覆草擬** | 對 client 的「配對進度更新」、對 worker 的「邀請信」、對逾期方的「溫和催辦」——AI **草擬好文字**，Edward 改一句就發（不自動發） | admin 一鍵發送 / 簡報附草稿 | `send-decision-email` / `notify-lead-slack` 已有發送管道 |
| A-4 | **對帳摘要** | AI 把當日金流狀態（應收/已收/待 ack/逾期）**摘要成 3 行人話**，標出對不上的地方，附 Edward 該做的動作（如「BP-xxx 抽佣已逾期 5 天，建議寄催款」） | 每日簡報「金流」段 | `commission_records` + 對帳欄位已有 |
| A-5 | **卡點偵測 + 建議動作** | AI 把 O-3 卡住的案**翻譯成 Edward 語言** + 給具體下一步（不只說「卡住了」，而是「BP-xxx 的 worker 簽約後 2 天沒動，建議今天 LINE 提醒一下」） | 每日簡報「該你處理」段 | doc 37 已盤點所有卡點類型 |

**克制聲明**：A-3 的草稿 AI 寫、Edward 發；A-1/A-2 的決策 AI 給建議、Edward 拍板。**沒有任何一條是 AI 替 Edward 對外發言或對外撥款**——這條線在 PMF 階段不能破，破了就是信任事故 + 法律風險。

## 3. 第三層 · 主動提醒人工（哪些非 Edward 不可 + 何時 + 用什麼形式）

### 3.1 非 Edward 不可的 4 件事（永遠人工）

| 動作 | 為什麼非人工不可 | 提醒形式 |
|---|---|---|
| **覆核 worker** | 認證是平台信任資產的根，AI 自吹偵測會漏、會誤判，最終把關必須是人 | 每日簡報（除非 > 72h 未審才升即時） |
| **確認配對** | 撮合決策牽涉檔期 / 化學反應 / 法律上「平台非服務商」的角色界線 | 每日簡報 + AI 預備好 Top 3 |
| **處理爭議 / 仲裁** | 涉及金流補償 + 雙邊信任，AI 不可判決 | **即時警示**（爭議不能等到隔天） |
| **確認撥款 / 抽佣** | 真金白銀進出，路徑 D 下還涉人工對帳，錯一筆是信任事故 | 每日簡報（除非異常金額才升即時） |

### 3.2 提醒形式分流原則 ⭐（這份藍圖最關鍵的設計決策）

> **核心判準：這件事「等到明天早上 9 點再看」會不會出事？**
> - **會出事 → 即時警示**（沿用現有 `notify-edward.ts` 即時 email，但收斂到只剩真急的）
> - **不會出事 → 收進每日簡報**（絕大多數事件歸這裡）

| 類別 | 走即時警示 | 走每日簡報 |
|---|---|---|
| **判準** | 安全/金流/法律風險、有時效硬上限、用戶端正在等且會流失 | 例行營運、可批次處理、隔天處理無損 |
| **例子** | 爭議進仲裁、admin 異常登入、防灌爆觸發、異常大額金流、worker accept 後 client 端正在焦慮等（影響轉換） | 新 worker 申請、新發案、milestone 交付、合約簽完、抽佣逾期、供需失衡、對帳摘要 |
| **數量目標** | **一天 ≤ 1-2 封**（吵 = 失效） | 1 封 digest 收全部 |

**對現有 `notify-edward.ts` 的策略性調整建議**（給卡西法）：現在 4 個事件全走即時 email，我建議**重新分流**——
- `contract_signed`（合約簽完）→ 改進每日簡報（簽完了不急，隔天 follow up 無損）
- `milestone_delivered`（交付）→ 改進每日簡報（有 7 天驗收窗，不急）
- `client_intake`（新發案）→ 可留即時（client 正在等、影響轉換），但也可進簡報——**Edward 拍板**
- `worker_apply`（新申請）→ 進每日簡報（72h 內審即可）

這樣即時 email 從「每天可能 N 封」收斂到「真的需要你立刻看的才響」，**Edward 的信箱重獲信任**——響了就是真的有事。

## 4. 第四層 · 每日營運簡報（核心交付）⭐⭐

### 4.1 推送時間與通道

- **時間**：每天台灣時間 **09:00**（cron）。對齊 doc 37 §五「Edward 每天 10:00 開 admin 輪詢」的習慣——**簡報比他開 admin 早一小時送到，他打開 admin 前就已經知道今天該看什麼。** 把「輪詢」變成「按圖索驥」。
- **通道**：主通道 **email**（沿用 `notify-edward.ts` 的 Resend + 同一套 dark theme HTML 模板，視覺一致）。後期 admin dashboard 加一個「今日簡報」卡片同步顯示（同一份資料兩個出口）。
- **週末**：照發但標「週末模式」（只報真異常，例行待辦壓縮）。Edward 不想被打擾可在 admin 設「週末靜音」。

### 4.2 簡報內容結構（5 段 · 從上到下就是 Edward 的閱讀動線）

```
┌─────────────────────────────────────────────┐
│  BEYONDPATH 每日營運簡報 · 2026-XX-XX (週X)    │
│  早安 Edward，今天平台這樣 ↓                    │
├─────────────────────────────────────────────┤
│  ① 一句話總結（AI 寫的人話）                    │
│     「今天 2 件事等你，最急的是審 1 位 worker    │
│      （已等 60h）。平台健康，無異常。」           │
├─────────────────────────────────────────────┤
│  ② 該你處理的事（按優先級排，最多列 5 件）        │
│     🔴 [覆核] worker 王小明 已等 60h            │
│         AI 初評：建議 approve（L8.2，無自吹旗標）│
│         → [開 admin 審核]                       │
│     🟡 [配對] 客戶 A 的 brief 待你確認           │
│         AI 已備好 Top 3：林xx(92)/陳xx(88)...   │
│         → [開 admin 看配對]                     │
│     🟡 [跟進] BP-3a2f 簽約後 worker 2 天沒動    │
│         建議：今天 LINE 提醒一下                  │
│         → [草稿已備 · 一鍵發]                    │
├─────────────────────────────────────────────┤
│  ③ 平台狀態快照（趨勢，不是絕對數堆砌）           │
│     在跑案件：3 件（1 簽約中 / 2 履約中）         │
│     本週新發案：2（上週 1 ↑）                    │
│     worker pool：4 approved                    │
│     本週 GMV：NT$ 0（尚無結案）/ 待收抽佣：NT$ 0 │
├─────────────────────────────────────────────┤
│  ④ 異常與警示（沒有就一句「今天無異常 ✓」）       │
│     ⚠️ 設計領域有 1 筆發案但池內 0 可配 worker   │
│        → 供給缺口，建議優先招募設計 worker        │
├─────────────────────────────────────────────┤
│  ⑤ 靜默信號（AI 替你注意「沒發生的事」）          │
│     · 已連續 4 天無新 worker 申請                │
│     · BP-3a2f 是本週唯一還在動的案               │
├─────────────────────────────────────────────┤
│  [開 admin 後台]   [本週完整儀表板]              │
└─────────────────────────────────────────────┘
```

### 4.3 五段設計邏輯（為什麼是這個順序）

1. **① 一句話總結**——Edward 30 秒掃完就知道今天要不要進 admin。這是整封簡報的靈魂，AI 用人話寫，**不是模板填空**。如果某天「無事」，就該老實說「今天平台安靜，無待辦，喝杯咖啡」。
2. **② 該你處理的事**——**按優先級排序**（紅 > 黃），每件附「AI 已備好的東西 + 一鍵動作連結」。這段直接對應 §3.1 的「非 Edward 不可」4 件事 + §2 的 AI 預備。**最多列 5 件**，超過收進「還有 N 件次要的，見 admin」——不淹沒。
3. **③ 平台狀態快照**——對齊蕪菁頭 doc 36 §六「每週儀表板」但**日頻化 + 報趨勢箭頭**（↑↓→），早期看絕對數 + 與上週比，不堆比率。
4. **④ 異常與警示**——對應 §1 的 O-5 + O-6，**沒有異常就明確說「無異常 ✓」**（報平安和報警一樣重要，Edward 才信這份簡報真的在看）。
5. **⑤ 靜默信號**——AI 的差異化價值在這裡，「沒發生的事」。這段是其他 dashboard 永遠給不了的。

### 4.4 簡報的語氣（品牌一致性把關）

簡報是 AI 助理「對 Edward 說話」——語氣要**像一個靠譜的營運長秘書，不是系統 log**。
- ✅「今天 2 件事等你」「平台安靜，無待辦」「設計領域缺人，建議優先招募」
- ❌「您有 2 筆待處理事項」「系統檢測到 0 筆異常記錄」（公文 / 機器味）

這跟 BeyondPath 整體「AI 原生 + 專業溫暖」定位一致——**連內部營運工具都該有溫度**，因為這是 Edward 每天第一個讀的東西。

## 5. 落地分期

### Phase 0 · 第一步最小可行（1-2 天 · 立刻有感）⭐

**只做一件事：一個每日簡報 Edge Function（cron 09:00），復用 `notify-edward.ts` 的 Resend 管道 + HTML 模板。**

- **資料來源**：直接查 Supabase 既有表（`worker_applications` / `client_intakes` / `contracts` / `milestones` / `commission_records`）——蕪菁頭 doc 36 §六已經把 SQL 都寫好了，直接搬。
- **內容**：先做簡報 §① + §② + §③（一句話總結 + 該你處理的事 + 狀態快照）。④⑤ 異常/靜默信號 Phase 1 再加。
- **「AI 一句話總結」怎麼做**：把當天查到的數字餵給一次 LLM call（Anthropic API 已接），讓它寫 §① 那句人話 + §② 每件事的「AI 初評/建議」。一天一次 call，成本可忽略。
- **為什麼這是最有感的第一步**：Edward 從「每天 10:00 開 admin 輪詢 5 個地方」變成「9:00 收一封簡報，知道今天就審 1 個 worker、確認 1 個配對」。**一個新檔、不動現有任何東西、不碰金流、不碰前端**——風險最低、體感最強。

**Phase 0 不做**：不重寫 `notify-edward.ts` 的即時分流（先讓簡報和現有即時 email 並存，Edward 用幾天後再決定要不要把 contract_signed / milestone_delivered 改進簡報）。不做 admin dashboard 卡片。不做 ML。

### Phase 1 · 觀察層補全 + 即時分流收斂（soft launch 後第 1-2 週）

- 補簡報 §④ 異常警示（接 O-5：rate limit / admin log / 仲裁 / 退件次數）+ §⑤ 靜默信號（O-6：供需失衡 / 連續無發案 / 無申請）。
- 按 §3.2 重新分流 `notify-edward.ts`：`contract_signed` + `milestone_delivered` 改進每日簡報，即時 email 只留真急的。
- 接 doc 37 A-2/A-3/A-6：milestone 狀態變化、簽約完成、worker ack 逾期——**全部進簡報而非各加一封即時 email**（這是我和馬魯克 A 清單的差異：他列「各加 Slack push」，我主張「收斂進一封簡報」，避免通知爆炸）。

### Phase 2 · 輔助層深化 + admin dashboard 同步（10-30 案階段）

- A-3 通知/回覆草擬接進 admin「一鍵發送」（草稿 AI 寫、Edward 改一句發）。
- A-1 配對推薦預備：新 brief 進來自動預跑配對，結果直接進簡報。
- admin dashboard 加「今日簡報」卡片 + 「在跑案件一覽表」（解 doc 37 §六「沒有一眼看清所有在跑案件的 dashboard」）。
- 簡報加「本週回顧」（每週一的簡報多一段週趨勢，餵養蕪菁頭北極星追蹤）。

### Phase 3 · 預測與主動建議（30+ 案 / PMF 站穩後 · 押後不超綱）

- 供需預測：「照這個趨勢，2 週後設計領域會缺人」。
- 案件健康預測：「這個案的退件節奏像會進仲裁，提前介入」。
- **這層在 PMF 階段一律不做**——數據量不夠，做了是炫技不是減負。明確押後。
