## 任務 2 · 數位簽約法律有效性判定（Edward Q1）

### 2.1 法源 — 台灣《電子簽章法》2024 修正版

2024-04-30 立法院三讀、2024-05-15 公布施行（全文 22 條，自公布日施行），是 2001 制定以來首次全文翻修。對 BeyondPath 最關鍵的兩點：

1. **§4 功能等同原則**：「電子文件及電子簽章，符合本法規定者，在功能上等同於實體文件及簽章，**不得僅因其電子形式而否認其法律效力**。」
   → 即：線上簽名圖 + hash + 時間戳這套，**不會因為它是電子的就被認定無效**。有效性沒問題。

2. **「數位簽章」vs「一般電子簽章」的關鍵分野（決定證據力高低）**：
   - **數位簽章**＝以數學演算法 + 簽署人**私密金鑰加密** + **經主管機關許可之憑證機構（CA）簽發之有效憑證**。法律賦予其「**推定為本人親自簽名或蓋章**」之效力（推定效力）。
   - **一般電子簽章**＝任何「依附於電子文件、用以辨識確認簽署人身分與文件真偽」的電子方式（含手寫簽名圖、勾選同意、上傳簽名照）。**有法律效力，但無「推定效力」**——發生爭議時，主張該簽名為真的一方**負舉證責任**。

### 2.2 BeyondPath 現況歸類

我把整條簽約鏈拆解（`generate-contract-pdf` → email signed link → `contract.html` 簽名 → `submit-signature` JWT 三層驗 + 簽名圖 + IP/時間 → `resend-contract-certificate` 憑證 → `contract-verify.html` 查驗）：

**歸類結論：BeyondPath 做的是「一般電子簽章」，不是法律意義的「數位簽章」。**
- 沒有經主管機關許可的憑證機構（CA）簽發的 PKI 憑證。
- `contract-jwt.ts` 的 HS256 JWT 是**平台對簽署連結的存取控制**（防偽連結、14 天 TTL、role 綁定），不是簽署人個人的非對稱金鑰簽章——它證明「這個簽署 session 是平台授權發出的」，不證明「簽的人就是合約當事人本人」。
- 簽名本體 = 上傳的手寫簽名圖 / canvas 手繪圖（`submit-signature` 第 338-360 行）。

**這完全符合 Edward 拍板的「自家簽 + 第三方時間戳」定位 —— 但有一個重要落差見 2.3。**

### 2.3 證據力四要件逐項評分

數位合約要在爭議中站得住，看四個維度：

| 要件 | 現況做法 | 評分 | 說明 |
|---|---|---|---|
| **① 完整性（Integrity）**<br>文件未被竄改 | PDF 產生時算 SHA-256 寫 DB（`generate-contract-pdf:385`）；雙方簽完算 final hash = `pdf_hash\|client_sig\|worker_sig\|client_ts\|worker_ts` 再 SHA-256（`submit-signature:382`）；公開 `contract-verify.html` 可任何人比對 | ✅ **強** | 這塊做得紮實。任何人可驗 PDF 是否平台正本，且簽名+時間綁進 final hash，事後改任一項 hash 就對不上 |
| **② 不可否認性（Non-repudiation）**<br>簽署人不能否認簽過 | 簽名圖 + IP 紀錄（`client/worker_signature_uploaded_ip`）+ 簽署時間 + `signature_attempts` 表記錄每次嘗試 + UA | 🟡 **中** | 有 IP + 時間 + 簽名圖佐證，但因非「數位簽章」，**無推定效力**，舉證責任在平台。IP 可被否認（共用網路/VPN），簽名圖可被否認（非本人筆跡）。對 PMF 夠，但不是鐵證 |
| **③ 身分連結（Authentication）**<br>簽的人=合約當事人本人 | 簽署連結走當事人 email（`generate-contract-pdf` Resend 寄到 snapshot.client_email/worker_email）+ JWT role 綁定 | 🟡 **中** | 「控制了該 email 信箱的人」≈ 當事人，這是 email-based 身分連結的常見強度。但無第二因素（沒有手機 OTP / 自然人憑證 / 證件核對），**email 被盜或代收即可冒簽**。是現況最弱的一環 |
| **④ 時間證明（Timestamp）**<br>簽署時間客觀可信 | `submit-signature:361` `new Date().toISOString()` | 🔴 **弱** | ⚠ **這是與 Edward 拍板的落差**：時間戳來源是 **Supabase Edge runtime 的系統時鐘**，是**平台自家時間**，不是「第三方時間戳」。雖然 Edward 說「自家簽 + 第三方時間戳」，但 code 裡**沒有接任何第三方 TSA（Time Stamping Authority）或可信時間源**。爭議時平台無法自證「這個時間沒被自己改過」 |

### 2.5 PMF 階段務實判定

**夠不夠用？→ 夠用。** 對 PMF 階段（個人營業者、Y1 台灣境內、ACV 通常數萬至十數萬的單案媒合），這套「一般電子簽章」在《電子簽章法》§4 下**有效、站得住**：
- 文件完整性（①）做到了商用級水準，比多數同規模平台強。
- 不可否認性（②）+ 身分連結（③）達到「協商與一般爭議調解夠用」的程度——配對紀錄 + 簽名圖 + IP + 時間 + 雙方存證副本，足以在大多數善意爭議中釐清事實。
- terms §3.5/§6 已誠實定位「合約存證僅作配對紀錄與爭議解決依據、不取代法律公證」——**這個定位是對的、誠實的，不要拿掉**。它讓平台不會被誤認為承擔了公證等級的責任。

**不需要過度到第三方憑證中心（CA）。** 接自然人憑證 / TWCA 等 CA 級數位簽章對 PMF 階段是過度投資——成本高、用戶摩擦大、且媒合單案金額不需要公證等級證據力。Edward 的方向判斷是對的。

### 2.6 證據力底線缺口 — 補什麼能更穩（不過度）

#### 🔴 應補（讓證據力達到 PMF 安全底線，2 項）

**缺口 A · 時間戳沒有第三方來源（對應 Edward 拍板的「第三方時間戳」未實作）**
- 現況：`submit-signature:361` 用系統時鐘。
- 風險：時間是平台自己寫的，平台理論上可竄改，自證力弱。
- **務實補法（低成本、不需 CA）**：簽署完成那一刻，把 final signature_hash 送一個**免費/低成本的第三方可信時間戳**蓋章。選項：
  - (a) 接 **freeTSA.org 或類似 RFC 3161 TSA**（免費，回傳 timestamp token，存進 DB）— 最正規，給 hash 蓋客觀時間。
  - (b) 把 final hash 寫到一個**外部不可竄改的公開記錄**（如送一封含 hash 的 email 到平台外部信箱、或寫進 git commit / 公開 log）— 最簡，建立「至少在 T 時刻此 hash 已存在」的旁證。
  - (c) 若要最強且仍低成本：把 final hash 錨定到公鏈 OpenTimestamps（免費、基於比特幣）。
  - **建議先做 (a) 或 (b)**，這正是 Edward 說的「第三方時間戳」，目前是承諾了但 code 沒做。**這是 Edward Q1 提到「自家簽+第三方時間戳」與現況的唯一實質落差，最該補。**

**缺口 B · 身分連結只有 email 單因素**
- 現況：誰控制該 email 信箱誰就能簽。
- **務實補法（不需 CA、低摩擦）**：簽署前加一道**寄到當事人 email 的一次性驗證碼（OTP）**或在簽名頁要求**重新輸入收件 email 比對**，把「控制信箱」這件事再確認一次 + 留痕。這比現在「點 email 連結就能直接簽」多一層身分綁定，且摩擦極低。進階可選簡訊 OTP（需手機號，摩擦稍高，PMF 可不做）。

#### 🟡 優化（再穩一點，非底線）

- **優化 a**：簽名頁加「☑ 我已閱讀並同意服務條款與本合約全部內容」勾選 + 把勾選狀態與時間寫進簽署紀錄。現況 `contract.html` 顯示了 PDF 與條款連結但**沒有明確的同意勾選留痕**。加這個對「明示同意」舉證很有幫助、成本極低。
- **優化 b**：把 UA、簽署裝置資訊、簽名圖的 EXIF/繪製軌跡（canvas 可記筆畫時間序）一併存證，強化「這是真人即時簽」的旁證。
- **優化 c**：`contract-verify.html` 目前比對的是 `pdf_hash`（合約 PDF 本體）。建議查驗頁也能比對 `signature_hash`（含簽名+時間的 final hash）— 目前查驗頁有顯示 signature_hash（line 215-221）但不接受用戶上傳簽名圖比對。屬 nice-to-have。

## 給主對話蘇菲的摘要

**Edward Q3（隱私/條款是不是真正式版了）：**
- **兩份條款本體（terms.html / privacy.html）= 真正式版**。逐行 + 全站 grep 掃過，**0 處 Beta/POC/不收費 等非正式殘留**，責任上限/退費/管轄/跨境/IP/cookie/審閱期等正式必要條款都齊。
- **但 Edward 直覺對了——還有「非正式殘留」，藏在條款下游**：用戶實際簽的**合約 PDF 本體 + 簽約 email + 發票**還是「Beta POC / Early Beta」，而且 `generate-contract-pdf` 印「BeyondPath 不收款、雙方直接轉帳」**跟條款已上線的綠界代收代付直接打架**。母法改好了、子文件沒同步。**這條正式上線必補，要卡西法改 code（我只標了位置，沒碰）。**
- 條款本體另外 2 項正式上線必補（都是小修）：① privacy §8 第三方揭露漏了 Resend + Anthropic（§4.1 有寫但 §8 沒列，個資法 §8 告知義務）；② 缺未成年/行為能力條款（涉金流+簽約的收費平台該有）。

**Edward Q1（數位簽約法律站不站得住）：**
- **站得住、有效。** 台灣《電子簽章法》2024 修法 §4：電子簽章「功能上等同實體簽章，不得僅因電子形式否認效力」。
- **但要說清楚定位**：BeyondPath 這套是「**一般電子簽章**」（簽名圖+SHA-256+時間戳），不是法律上的「數位簽章」（需 CA 憑證+PKI）。差別＝一般電子簽章**有效但無「推定效力」**，爭議時舉證責任在平台。**對 PMF 階段這完全夠用，不需要過度上憑證中心——Edward 的方向是對的。**
- **證據力四要件**：完整性 ✅強（hash+公開查驗做得好）／不可否認 🟡中／身分連結 🟡中（只有 email 單因素）／**時間證明 🔴弱**。
- **最該補的一件**：Edward 當初拍板「自家簽 + **第三方時間戳**」，但 code 裡時間戳是**平台自己的系統時鐘，第三方時間戳沒做**。補一個免費 RFC 3161 TSA（如 freeTSA）或把 final hash 錨到外部不可竄改記錄即可，低成本，補完證據力底線就穩。第二件：簽署前加一道 email OTP 把身分再綁一次（低摩擦）。

**各自最該補（一句話）：**
- 條款：合約 PDF/email 去 Beta + 修「不收款」與代收代付的矛盾（卡西法改 code）。
- 簽約：把承諾的「第三方時間戳」真的接上（freeTSA / OpenTimestamps，免費）。
